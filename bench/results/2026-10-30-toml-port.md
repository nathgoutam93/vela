# The TOML 1.0 package: conformance, robustness, speed and memory

`packages/toml` reads TOML 1.0 into a `Value` (`toml.parse`), offers
lookups (`get`, `lookup("server.port")`, `as_int`, ...), and writes a table
back as TOML (`toml.write`). `bench/real/toml` is a decoder with the interface
toml-test expects (TOML on stdin, tagged JSON on stdout, exit 1 for an invalid
document). It also has `--write` to write the document back, and `--check` to
parse only. Host: Intel Xeon @ 2.10 GHz, Linux 6.18 x86-64, gcc 13.3, Python
3.13.

## Conformance

`tests/toml_test.py` runs the TOML 1.0 cases of toml-test v2.2.0
(`tests/fixtures/toml-test`, MIT). The results are the same through C,
natively, and through C under ASan+UBSan with leak detection:

| | Pass |
| --- | ---: |
| valid documents: values as tagged JSON | 205 / 205 |
| the same, written back by `toml.write` and read again | 205 / 205 |
| invalid documents: rejected with exit 1 and a message | 474 / 474 |
| stress documents (100,000 keys, 30,000 tables and array tables, 2 MB strings, nesting of 120), each in under 10 s | 9 / 9 |
| nesting of 100,000: rejected cleanly, not a stack overflow | 2 / 2 |

The comparison is toml-test's own: integers and floats by value, offset
datetimes as instants, everything else exactly. To check that the harness
discriminates, a fake decoder that prints `{}` for every input fails all 474
invalid cases and 198 of the 205 valid ones.

## Against Python's tomllib

`python3 tests/toml_test.py --fuzz N --seed S` mutates the valid documents
(single bytes and pieces of other documents inserted, removed or repeated)
and compares each with Python's tomllib, another TOML 1.0 parser. Over
eight seeds, 38,000 mutated documents: about 18.5% were accepted by both
with the same values, the rest rejected by both. None crashed, panicked or
hung. Two kinds of disagreement turned up and are settled:

- newlines inside multi-line strings: tomllib reads CRLF as LF, and the
  package kept CRLF. The specification allows either; the package now reads
  LF, so a value does not depend on how git checked the file out.
- integers beyond 64 bits: tomllib reads any size. TOML 1.0 requires an
  error for an integer that cannot be kept losslessly, as the package
  gives, and the fuzzer treats tomllib's acceptance as a rejection.

## Speed and memory

A 10.8 MB lockfile-style document: 40,000 `[[package]]` tables with
strings, arrays and checksums, and some nested tables with datetimes and
inline tables.

| | Parse | Parse + tagged JSON | Peak memory |
| --- | ---: | ---: | ---: |
| Vela, native | 0.153 s (70.9 MB/s) | 0.330 s | 131 MiB |
| Vela, through C | 0.160 s (67.8 MB/s) | 0.380 s | 130 MiB |
| Python tomllib | 1.417 s (7.7 MB/s) | | 63 MiB |

The first version parsed at about 16 MB/s with JSON output; its profile
pointed at three costs, now gone:

- a builder for every string, even one without escapes; such a string is now
  a slice of the document;
- a map key made for every lookup in a table; tables of up to eight keys are
  now searched in turn;
- two empty arrays allocated for every value, now shared.

The parser runs 95 instructions per input byte under callgrind, down from
167. The json package's `show` and `pretty` now copy runs of bytes that need
no escape, rather than one byte at a time. Memory stays at twice tomllib's
because of the size of `Value`, which is TL-117.

## Friction found

| Entry | What |
| --- | --- |
| TL-116 | String literals have no `\u{...}`: tests of escaping cannot name DEL or U+0001 |
| TL-117 | An enum is as large as its largest payload: `Datetime` makes every `Value` 88 bytes |
| TL-118 | `vela fmt` failed (E5001) on a file without a final newline; fixed |
| TL-119 | Found by the differential run validating this work: optimized native code gave a wrong value, from TL-111's edge blocks; fixed |

Structural `==` on Options, arrays and enums would have shortened the
package's tests, but the specification rules it out by design (see TL-047).
