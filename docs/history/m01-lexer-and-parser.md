# M1: lexer, Pratt parser, AST and C code generation

M1 turns Vela into a language. It is a tiny one: integers, `+ - * / %`,
unary minus, parentheses and `print`. But every stage of a real compiler
is now in place, and every later milestone extends these same files rather
than adding new stages.

Done when: `print(1 + 2 * 3)` prints 7, and errors point to line:col.

```
$ cat a.vl
print(1 + 2 * 3)
$ python3 stage0/main.py run a.vl
7
$ printf 'print(1 +)\n' > b.vl && python3 stage0/main.py run b.vl
b.vl:1:10: error: expected expression, found ')'
```

Files in this milestone:

| File | What it is |
| --- | --- |
| `stage0/lexer.py` | Bytes → tokens, including the newline rule |
| `stage0/parser.py` | Tokens → AST: recursive descent plus a Pratt expression parser |
| `stage0/ast_nodes.py` | The AST node types and the `vela ast` dump |
| `stage0/checker.py` | Rejects programs that parse but make no sense |
| `stage0/codegen_c.py` | AST → C |
| `runtime/vela_rt.h`, `vela_rt.c` | Checked arithmetic, panics, printing |
| `tests/run`, `tests/fail`, `tests/dump` | 48 golden tests |

## 1. The pipeline on one line of code

Every program goes through four steps. Here is `print(1 + 2 * 3)` at each
one, as printed by the driver's debugging commands.

**Tokens** (`vela tokens a.vl`): the lexer cuts the bytes into words.

```
1:1 ident print
1:6 (
1:7 int 1
1:9 +
1:11 int 2
1:13 *
1:15 int 3
1:16 )
1:17 ; (newline)
2:1 eof
```

**Syntax tree** (`vela ast a.vl`): the parser finds the structure. The
`*` sits below the `+` because it binds tighter.

```
(call print (+ 1 (* 2 3)))
```

**Checking**: `print` exists and takes one argument, and that argument is a
value. This step prints nothing when the program is fine.

**C** (`vela c a.vl`): the code generator walks the tree and emits C.

```c
// Generated by the Vela stage 0 compiler. Do not edit.
#include "vela_rt.h"

int main(void) {
    // line 1
    int64_t _t1 = vela_mul(2, 3, "a.vl:1:13");
    int64_t _t2 = vela_add(1, _t1, "a.vl:1:9");
    vela_print_int(_t2);
    return 0;
}
```

The rest of this document goes through the steps in order.

## 2. The lexer

### Why there is a separate lexing step

A parser could read characters directly, but then every grammar rule would
have to deal with whitespace, comments and spelling out multi-character
words. Splitting the work keeps both halves simple. The lexer knows what a
number looks like; the parser knows what an expression looks like. Almost
every production compiler is built this way.

A **token** is a `kind` plus the exact `text` and its `line` and `col`
(`Token` in `lexer.py`). Kinds are `ident`, `int`, `eof`, each keyword
(`fn`, `match`, ...), and each punctuation symbol (`(`, `+`, ...). Keywords
and symbols use their own spelling as their kind, so the parser can write
`tok.kind == "+"` instead of looking up a constant.

### Bytes, not characters

The lexer reads the file as `bytes` and never decodes it. This is a
decision with a reason that only shows up at M8: Stage 1 will be written in
Vela, where a `Str` is bytes and `src[i]` is a `Byte`. It will scan source
byte by byte, and differential testing requires both compilers to report
identical positions. So columns count bytes, from 1, in both. A tab counts
as one column, as in gcc. Non-ASCII bytes are allowed only in comments until
string literals exist.

`peek()` returns `-1` past the end of the input. Using `0` instead, as C
lexers often do with a NUL terminator, would make a stray NUL byte in the
file look like the end of the input. With `-1`, a NUL byte is reported as
`unexpected control byte 0x00`.

### The main loop

`Lexer.run` looks at one byte and decides what kind of token starts there:

| First byte | Action |
| --- | --- |
| space, tab, `\r` | Skip. `\r` is skipped so Windows line endings work (`tests/run/crlf.vl`) |
| `\n` | Maybe insert `;` (the newline rule), then start a new line |
| `//` | Skip to the end of the line, leaving the `\n` for the next step |
| digit | `number()` |
| letter or `_` | `identifier()`, then check whether the word is a keyword |
| one of `( ) + - * / % , ;` | A one-byte token |
| anything else | Error |

Each scanner takes the longest run of bytes that fits, a rule called
**maximal munch**. `printx` is one identifier, not `print` then `x`. When
we add `==` in M2, it will be one token, not two `=`.

### Keywords

All 13 bootstrap keywords are reserved now, even though M1 gives meaning to
none of them. If `match` were an ordinary name today, someone could write a
program using it as a variable, and M4 would break that program. Reserving
early costs nothing. `tests/fail/keyword_as_name.vl` checks it.

### Numbers

Integer literals are decimal digits, checked three ways:

- **Too large:** a literal must fit in `Int` (`INT_MAX = 2**63 - 1`).
  There is a catch: `-9223372036854775808` is unary minus applied to
  `9223372036854775808`, which does not fit. C has the same problem, which
  is why `INT64_MIN` is defined as `(-9223372036854775807 - 1)`. Go avoids
  it by evaluating constant expressions at arbitrary precision. Rust
  special-cases a minus sign in front of a literal. We follow C, the
  simplest option, and `tests/run/int_limits.vl` shows how to write it.
- **Leading zeros** like `007` are rejected. In C and Go, `010`
  is octal 8, a classic surprise. Rejecting it now leaves room for `0x`, `0o`
  and `0b` prefixes later without ambiguity.
- **Letters after digits**, as in `12abc`, are reported as one bad number.
  Lexing it as `12` then `abc` would produce a confusing parser error about
  an identifier.

### The newline rule

The locked decision is Go's automatic semicolon rule. The parser always
sees statements separated by `;`, but the lexer inserts most of them:

> When the lexer reaches a newline (or the end of the file), it inserts a
> `;` if the line's last token is an identifier, an integer, `)`, or one of
> `break`, `continue`, `return`.

The set is `ENDS_STATEMENT` in `lexer.py`. These are exactly the tokens
that can end a statement. Go's list also has string literals, `]`, `}`,
`++` and `--`. Ours gains `]`, `}` and Str literals when they arrive, and
`?` in M7, because `let n = parse(x)?` ends with it.

What follows from the rule:

- **A line ending in an operator, `(` or `,` continues.** None of those
  can end a statement, so no `;` is inserted:

  ```
  print(1 +
      2)
  ```

- **A line *starting* with an operator does not continue the previous
  line.** `print(1` followed by `+ 2)` on the next line gets a `;` after
  the `1`, and the parser reports `expected ',' or ')' in argument list,
  found newline` (`tests/fail/newline_before_operator.vl`). Go behaves
  the same way, and it is why Go style puts operators at the end of a line.
- **Trailing commas are allowed in argument lists.** Without them, a
  multi-line call could not end with its last argument on its own line,
  because the newline after that argument would insert a `;`:

  ```
  print(
      10,
  )
  ```

- **Explicit `;` still works** for several statements on one line:
  `print(1); print(2)`. An inserted semicolon and a typed one are the same
  token kind. Only their `text` differs (`"\n"` or `""` instead of `";"`),
  so error messages can say "found newline" or "found end of file".

The rule is a pure lexer rule: it looks at one previous token and needs no
knowledge of the grammar. That is the reason Go chose it, and why it is a
good lexing lesson. JavaScript's automatic semicolon insertion is the
opposite design. It inserts a semicolon only when the parser hits an error,
which ties it to the grammar and is famous for surprises such as `return`
on a line by itself.

*Planning note:* the roadmap lists the newline rule in M2. I moved it into
M1 because M1 programs already have several statements and need some way
to separate them. M2 has nothing left to do here.

## 3. The parser

### Recursive descent for statements

A **recursive descent** parser has one function per grammar rule, and the
functions call each other the way the rules refer to each other. The M1
grammar is small:

```
program   = { statement ";" } EOF
statement = expression
arguments = [ expression { "," expression } [ "," ] ]
```

`Parser.program` loops: skip empty statements, parse one statement, then
require a `;` (usually one the lexer inserted) or the end of the file. That
requirement is what rejects `print(1) print(2)` on one line. M2 adds `let`,
`if`, `for` and functions as more branches in `statement`.

### Pratt parsing for expressions

Expressions are the hard part, because of precedence (`*` before `+`) and
associativity (`10 - 3 - 2` is `(10 - 3) - 2`). The textbook
recursive-descent answer is one function per precedence level:
`expression` calls `term` calls `factor`, and so on. That works, but adding
an operator means adding a function, and C has 15 levels.

A **Pratt parser** (Vaughan Pratt, 1973) replaces the ladder of functions
with a table. Each infix operator has a pair of **binding powers**, a left
one and a right one, and higher means tighter:

```python
INFIX = {
    "+": (10, 11), "-": (10, 11),
    "*": (20, 21), "/": (20, 21), "%": (20, 21),
}
PREFIX = 30   # unary minus
POSTFIX = 40  # calls
```

The whole algorithm is `Parser.expression(min_bp)`:

1. Parse a **prefix**: a number, a name, `-` followed by an operand, or
   `( expression )`.
2. Look at the next token. If it is an operator whose left power is at
   least `min_bp`, consume it, parse the right side with
   `expression(right_power)`, combine the two into a `Binary` node, and
   repeat step 2.
3. Otherwise stop and return what you have. The caller deals with the
   operator.

`min_bp` reads as "only take operators at least this strong". Here is
`1 + 2 * 3`, starting from `expression(0)`:

```
expression(0): prefix 1
  sees +, left power 10 >= 0: take it, parse the right side with expression(11)
    expression(11): prefix 2
      sees *, left power 20 >= 11: take it, parse the right side with expression(21)
        expression(21): prefix 3; sees end of input, returns 3
      builds (* 2 3); sees end of input, returns it
  builds (+ 1 (* 2 3))
```

And `10 - 3 - 2`:

```
expression(0): prefix 10
  sees -, left power 10 >= 0: take it, parse the right side with expression(11)
    expression(11): prefix 3
      sees -, left power 10 < 11: stop, return 3
  builds (- 10 3), then the loop sees the second -, left power 10 >= 0: take it
    expression(11): prefix 2; returns 2
  builds (- (- 10 3) 2)
```

The right power being one more than the left is what makes an operator
left-associative. When the right side is parsed, an operator of the same
strength is not strong enough to join it, so it is left for the outer loop,
which attaches it to everything parsed so far. A right-associative operator
such as `**` in some languages would use `(30, 30)` instead.

**Prefix operators** parse their operand with their own power:
`-` calls `expression(30)`, so in `-2 * 3` the `*` (20) is too weak to join
the operand, and the result is `(* (- 2) 3)`.

**Calls are postfix operators**: `(` after an expression with power 40.
Since 40 beats unary minus, `-f(1)` is `-(f(1))`. In M4, field access
`a.b` and indexing `a[i]` go in the same branch.

**Parentheses leave no node.** `( expression )` resets the minimum power to
0 inside the parentheses and returns the inner expression unchanged. The
tree's shape already records the grouping, so `(1 + 2) * 3` dumps as
`(* (+ 1 2) 3)`.

Pratt parsing is the same algorithm as *precedence climbing*, written
differently. Dijkstra's *shunting-yard* algorithm reaches the same result
with an explicit operator stack instead of recursion. Pratt's version won
in hand-written compilers because new operators are one table entry and
the code stays readable.

### Error messages

Every parse error has the form `expected X, found Y`, where Y comes from
`lexer.describe(tok)`: `identifier 'x'`, `integer 12`, `')'`,
`keyword 'match'`, `newline`, `end of file`. Naming the token that was found
matters most when it is invisible. "found newline" is what explains why
`print(1` followed by `)` on the next line fails. An unclosed `(` also names
where it was opened: `expected ')' to match '(' at 2:7, found newline`.

M1 stops at the first error. Reporting several errors per run needs
*error recovery* (skipping ahead to a safe point and continuing), which is
in M3.

## 4. The AST

`ast_nodes.py` has five expression nodes (`IntLit`, `Name`, `Unary`,
`Binary`, `Call`), one statement node (`ExprStmt`) and `Program`.

- **Positions.** Every expression node has `line` and `col`. For operators
  it is the operator's own position (the `+` in `a + b`), not the start of
  the expression. Then `1 / 0` panics at the `/`, and in `1 + x` the error
  points at `x`. A `Call` uses its callee's position, so arity errors point
  at the function's name.
- **Plain records.** The nodes are dataclasses with no methods. The
  checker and code generator switch on the node type with `isinstance`. In
  Stage 1 that becomes a Vela `enum` with a payload per variant and a
  `match`, a direct translation. Python's other option, a method per node
  type or a visitor class, has no equivalent in Vela.
- **Named `ast_nodes.py`, not `ast.py` as the roadmap's layout says.**
  Python searches a script's own directory before the standard library. An
  `ast.py` in `stage0/` would replace the standard `ast` module, which
  `dataclasses` imports through `inspect`, and the compiler would crash on
  startup. Likewise there is no `token.py`.
- **The dump format** is an S-expression per statement: an operator and
  its operands in parentheses, operator first. It shows the tree's
  structure with no ambiguity, which is what precedence tests need
  (`tests/dump/ast_precedence.vl`).

## 5. The checker

Some programs are grammatically fine but meaningless: `prnt(1)`,
`print(1, 2)`, `print(x)`. Rejecting them is the checker's job. The parser
only knows about shape. M1's checker is small: there is one type, `Int`, and
one function, `print`, which returns nothing. `BUILTINS` maps each function
name to its parameter types and result type. The checker reports:

| Program | Error |
| --- | --- |
| `prnt(1)` | `undefined function 'prnt'` |
| `print(x)` | `undefined name 'x'` |
| `print(1, 2)` | `print expects 1 argument, got 2` |
| `print(1 + print(2))` | `print(...) does not produce a value` |
| `print(print)` | `'print' is a function; call it as print(...)` |
| `print(5(1))` | `only a named function can be called` |
| `1 + 2` on its own line | `this value is not used; only a call can stand alone as a statement` |

The last one follows Go: a statement that computes a value and discards it
is almost always a mistake. M3 turns this file into the real type checker,
and `check_expr` returning a type is already its shape.

## 6. Code generation

### One temporary per operation

`CodeGen.expr` walks the tree and returns, for each expression, a C
expression for its value. That returned expression is always a literal
(`2`) or a temporary (`_t1`). Each operation is emitted as its own C
statement whose result goes into a fresh temporary.

The obvious alternative, nested C expressions such as
`vela_print_int(vela_add(1, vela_mul(2, 3, ...), ...))`, is shorter, but it
has a real problem: **C does not specify the order in which a function's
arguments are evaluated.** In `vela_add(vela_div(1, 0, ...), vela_div(2, 0, ...))`,
gcc may run either division first, and clang may pick differently. Today
that only changes which panic you see. Once functions have side effects
(M2), it would change what programs do.

Emitting one statement per operation in tree order makes Vela's
evaluation order **left to right**, on every C compiler.
`tests/run/eval_order.vl` checks that `print(1 / 0 + 2 / 0)` panics at the
first `/`. The temporaries cost nothing at run time, because gcc removes
them. They will also help in M5: reference counting has to release every
intermediate value, and a named temporary is easy to release.

Temporaries are named `_t1`, `_t2`, and so on. C reserves identifiers
starting with `_` only at file scope (plus `_` followed by a capital letter
or a second `_`, everywhere), so these names are safe inside `main`. User
names will need mangling in M2, so that a Vela variable called `int` or
`printf` cannot collide with C.

Each Vela statement is preceded by a `// line N` comment, so the C can be
read side by side with the source.

### Checked arithmetic

The generated code never uses C's `+`, `-`, `*`, `/` or `%` on `int64_t`
directly. It calls `vela_add` and friends in `vela_rt.h`. The reason is
**undefined behaviour**: in C, signed integer overflow is not an error and
does not wrap. The program is simply invalid, and the optimizer may assume
it never happens. gcc really will turn `if (x + 1 > x)` into `if (1)`. If
Vela compiled `a + b` to C's `a + b`, every Vela program that overflowed
would have undefined behaviour.

So every operation checks first:

| Operation | Rule |
| --- | --- |
| `a + b`, `a - b`, `a * b` | Panics on overflow. Uses `__builtin_*_overflow`, which gcc and clang both provide; C23 standardises it as `ckd_add` |
| `a / b` | Truncates toward zero (`-7 / 2 == -3`). Panics if `b == 0`, or for `INT64_MIN / -1`, whose result does not fit |
| `a % b` | Takes the sign of `a` (`-7 % 3 == -1`). Panics if `b == 0`. `INT64_MIN % -1` is undefined in C, so `b == -1` returns 0 directly |
| `-a` | Panics for `INT64_MIN` |

Division and remainder match C, Go, Rust and Java. Python's `//` and `%`
round toward negative infinity instead, so stage 0 must never do Vela
arithmetic with Python's operators. It does none at all: it only prints
numbers into C.

These are `static inline` functions in the header, so after `-O2` they
compile to an add and a branch on the overflow flag. Running the whole test
suite with `-fsanitize=undefined,address` passes, which confirms the
generated code and the runtime have no undefined behaviour on these tests.

### Panics

A **panic** is Vela's response to a bug in the program. It is not an
error to handle. The locked decision is "panics only for bugs", and overflow
and division by zero are bugs. `vela_panic` flushes stdout (so everything
already printed appears first), prints
`file.vl:line:col: panic: message` to stderr, and exits with code **101**.
The format matches compile errors, so the same tools can jump to the spot.
Code 101 is Rust's choice. It is distinct from 1, which programs will
commonly use for their own errors from M7.

The location is passed to each runtime function as a string literal.
`c_string` builds that literal from the file name and escapes `"`, `\`, any
byte that is not printable ASCII, and also `?`, because `-std=c11` enables
trigraphs, and `??/` in a file name would turn into a backslash.

### print

`print(x)` prints an `Int` in decimal followed by a newline, using
`PRId64` from `<inttypes.h>` (`%ld` is wrong on Windows, where `long` is 32
bits). Once `Str` and `Bool` exist, `print` will accept them too, and the
checker will choose the runtime function from the argument's type.

## 7. Tests

| Directory | Count | Covers |
| --- | --- | --- |
| `tests/run` | 20 | Precedence, associativity, unary minus, division and remainder signs, Int limits, comments, the newline rule, CRLF, tabs, left-to-right panics, every overflow and division panic |
| `tests/fail` | 26 | Every lexer error, every parser error, every checker error, each with its exact line:col |
| `tests/dump` | 2 | The token stream with inserted semicolons; AST shapes for precedence, associativity, prefix and postfix |

`tests/dump/` is new in M1. A dump test has a `// dump: tokens` or
`// dump: ast` line, and its `// out:` lines are compared against what
`vela tokens` or `vela ast` prints. These tests check the lexer and parser
directly, not through program output, so `10 - 3 - 2` can be checked to
parse as `(- (- 10 3) 2)` rather than inferred from the printed 5. From M8
the same dumps are what Stage 0 and Stage 1 must agree on.

Besides the suite, I ran the front end on 200,000 random token sequences.
Every one either compiled or produced a `CompileError`; none crashed the
compiler.

## 8. What real compilers do differently

- **Positions.** We store line and column in every token. rustc, Clang
  and Go store a single byte offset into the file (rustc's `Span`, Clang's
  `SourceLocation`). Line and column are computed only when an error is
  printed, by searching a table of line-start offsets. That makes tokens
  smaller and a span can cover a range. For a compiler our size,
  line:col is simpler to read and debug.
- **Lexing on demand.** We lex the whole file into a list first. Clang and
  Go's parser pull one token at a time from the lexer, which saves memory on
  huge files. A list is easier to inspect and to dump.
- **Error recovery.** Production parsers keep going after an error so one
  run reports many problems. M3 adds this. It is harder than it sounds:
  bad recovery produces a flood of follow-on errors caused by the first.
- **Source snippets.** rustc and clang print the offending line with a
  `^` under the column. The one-line format comes first because the tests
  compare it exactly. Snippets can be added on top later; agent-friendly
  JSON diagnostics are planned for M10.
- **Constant overflow at compile time.** Go rejects `9223372036854775807 + 1`
  at compile time, because it evaluates constant expressions exactly. We
  compile it and panic at run time (`tests/run/panic_add.vl`). Constant
  folding with overflow checking would be a natural addition to the checker
  later.
- **Overflow policy.** Swift traps on overflow, as we do. Rust traps in
  debug builds and wraps in release builds for speed. Go and Java always
  wrap silently. C leaves it undefined. Trapping costs a predictable branch
  per operation, which is cheap on modern CPUs.
- **Mapping C back to Vela.** Compilers that emit C (Nim, early C++) can
  emit `#line 12 "a.vl"` directives, which make gcc's own errors and gdb's
  stepping refer to the Vela source instead of the C. We emit
  `// line N` comments instead, which are easier to read while learning.
  Switching to `#line` is a small change once we want debugger support.
- **Intermediate representations.** We go straight from the AST to C.
  Real compilers lower the AST through one or more IRs (Rust: HIR, MIR, then
  LLVM IR) where checking and optimisation are easier. Our temporaries are a
  small step that way, since each line of output is one operation. M11's
  native backend builds a real IR.

## 9. Decisions made in M1, and changes from the plan

These are recorded in the roadmap's "Decisions locked in now" table:

| Decision | Reason |
| --- | --- |
| Int overflow, division by zero and `INT64_MIN / -1` panic, with the source position; panics exit with 101 | Signed overflow is undefined behaviour in C; silent wrapping hides bugs; "panics only for bugs" |
| Evaluation order is left to right; codegen puts each operation in its own C statement | C leaves the order of argument evaluation unspecified |
| Source is read as bytes; columns count bytes from 1 | Stage 1 scans bytes; both stages must report identical positions |

Smaller choices, made here and easy to revisit:

- `print` appends a newline, and accepts only `Int` for now.
- Integer literals with leading zeros (`007`) are rejected.
- A bare value such as `1 + 2` is not allowed as a statement.
- Compile errors exit with 1, internal compiler errors with 70.

Changes to the plan:

- `stage0/ast.py` is `stage0/ast_nodes.py`, because of the standard-library
  clash explained in section 4.
- The newline rule was implemented in M1, not M2 (section 2).
- `tests/dump/` was added next to `tests/run/` and `tests/fail/`
  (section 7).

## 10. Questions for you before M2

1. **Top-level statements or `fn main`?** In M1 a program is a list of
   statements that run in order. Once M2 adds functions, I suggest
   requiring `fn main()` and allowing only declarations at the top level,
   as Go and Rust do. It keeps "what runs when" obvious and matches what
   the compiler itself will look like. The M1 tests would then be wrapped
   in `fn main() { ... }`. Alternatively, keep script-style top-level code.
2. **Constant overflow:** should `print(9223372036854775807 + 1)` be a
   compile-time error, as in Go, or is the runtime panic enough for now?
3. **`print` and newlines:** keep `print` as "value plus newline" until
   string building exists (M5/M7), or add a separate non-newline variant
   later?

**Answered after M1:** use `fn main`; the runtime panic is enough for
constant overflow; `print` keeps its newline. M2 implements the first
(see `m02-functions-and-control-flow.md`).
